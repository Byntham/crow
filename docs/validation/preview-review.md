# Crow reviews its runtime feature

On 19 September 2026, PR12 was marked ready and reviewed by both the existing inspection-only Crow and a separate installation built from commit `7592cfd5cf0b173724820f1c6e1a368f02ccfbe6` with runtime testing enabled.

The preview uses separate service state, provider sessions, Podman storage and a loopback port. A deployment-only patch gives its GitHub status and review markers a distinct namespace and visible "Crow runtime preview" label. It does not change the existing App webhook. A PR12-only watcher requests reviews for new head/base combinations and stops the preview after GitHub confirms merge. These deployment files are outside the repository.

## Observed first review

The [preview review](https://github.com/Byntham/crow/pull/12#pullrequestreview-5254959399) performed seven experiments without a supplied test recipe:

- Fetched Rust dependencies at head and base.
- Attempted the complete Rust suite at both revisions. Both failed because the managed image has Rust 1.87 and Crow requires 1.88 or newer. An attempted toolchain download was rejected by the package gateway. The report identified this coverage gap rather than attributing it to the PR.
- Ran focused Python package-cache and source-restoration probes successfully.
- Generated the checkout fixture, ran both Chromium smoke tests, saved both screenshots and inspected them through two successful native-image `read_artifact` calls.

The seven receipts recorded four successful commands and three failed commands, counting setup separately from tests. After report acceptance, the preview removed all prepared snapshots and retained the receipts and two screenshots. Cleanup recorded no warnings. The inspection-only review and preview each kept their own status comment.

These observations verify execution, failure diagnosis, before/after investigation, image delivery, publication and completed-review cleanup. They do not establish that Crow's full Rust suite ran inside the managed image, or that the reviewers' findings were discovered dynamically. Both reviewers labelled their findings as inspection-based.

## Findings addressed

The [existing Crow review](https://github.com/Byntham/crow/pull/12#pullrequestreview-5254948111) identified mismatched TLS names through CONNECT tunnels, Go ZIP directory checksum handling, partial exports surviving maintenance, and nested scripts losing the selected npm version. The preview identified dependency-socket access under SELinux and runtime receipt appendices exceeding whole-report size limits.

The follow-up adds bounded TLS ClientHello/SNI validation, hashes Go directory entries against independently verified Go checksums, removes partial exports from validated nested directories, and preserves the pinned package manager in nested scripts. Report appendices must fit whole-report validation; a full valid model report takes precedence over optional appended rows.

SELinux support remains conditional on host policy. Private socket relabeling and an explicit connection preflight improve compatibility and diagnostics without disabling container labeling. No enforcing SELinux host was available for validation; mock permission failures and ordinary rootless containers cover the implemented paths.

TLS stays end-to-end. The gateway cannot inspect encrypted HTTP Host headers or prevent uploads or domain fronting offered by an allowed endpoint. The runtime guide documents that boundary.

Generated screenshots and raw reports remain outside the current source tree. The historical visual evidence stays accessible through immutable commit links in the other validation notes.

## Final cache simplification

The later inspection review identified a provenance gap in Cargo reuse. An unused repository lockfile could authorize a prepared archive without independently authenticating its registry origin. The earlier registry-directory and checksum checks do not close this gap. An independent audit found the same distinction in Go's `checkModSum` and npm's integrity-addressed cache reads: a repository-chosen checksum can match substituted bytes even when a fresh registry download would fail.

Cross-review package sharing has therefore been removed for every package manager. The archive importer/exporter and its verification machinery are deleted. Each review installs dependencies afresh; successful preparations remain reusable within that review, and the toolchain image remains shared. Maintenance deletes obsolete shared package/workspace archives while preserving unrelated files and image records. Earlier cache reuse observations above are historical and no longer describe the final implementation.

The Rust/Go and updated-PR npm scenarios now require fresh cache directories and installation, then run tests offline. They retain checks for completed, paused and superseded review cleanup. This trades repeated downloads for predictable review isolation and removes over two thousand lines of cache code and associated tests.

The final simplified implementation passes 308 retained ordinary tests, formatting and all-target clippy. All five managed-container scenarios passed in 177 seconds, including fresh npm/Cargo/Go installation in a second review, offline tests, Chromium evidence, source restoration, and completed/paused/superseded snapshot cleanup. The test count decreased because tests for the removed archive transfer feature were removed with it.

The next inspection review found that overflowing the MCP request queue terminated the review. Crow now returns a queue-full JSON-RPC error only for excess requests, preserving accepted work and the connection. A deterministic 20-request burst verified four correctly identified errors, sixteen accepted responses, explicit runtime cancellation and subsequent connection reuse. All 309 ordinary tests, formatting and clippy pass.

The runtime preview then demonstrated that repeating a root package-manager pin does not establish a separate workspace. An additional Yarn probe confirmed that a member's own lockfile can also coexist with root ownership. Discovery now withholds command candidates for nested pins or lockfiles beneath an outer workspace declaration and asks the reviewer to inspect ownership. It preserves ordinary standalone setup and supported unambiguous workspace candidates. Both real Yarn fixtures passed, including root installation with repeated pins and a nested lockfile; ten discovery unit tests cover the conservative boundaries. An independent audit found no remaining blocker in that lookup.

The queue and workspace follow-up passes all 310 ordinary tests, formatting and all-target clippy.

The following inspection review found three bounded issues. Public IPv6 allocations within `2001::/16` are now allowed while specific special-purpose and documentation prefixes remain blocked. Root pnpm workspace declarations now receive the same inspection warning as nested declarations. MCP responses now use a bounded outbox with persistent partial-write offsets, polled alongside tool execution and input; a client that stops reading cannot stop active deadlines or cancellation cleanup. Regressions filled stdout before cancellation and EOF, verified lock release before draining output, checked complete JSON responses and reused the connection. All 315 ordinary tests, formatting and clippy pass.

The real Podman MCP lifecycle scenario also passed after the outbox change, including isolated workspaces, interruption cleanup and subsequent experiments.


The runtime report presentation now uses short check descriptions and plain-language revision labels. Setup counts remain separate from test-command counts. The wide command table is replaced by an expandable diagnostics section, and reviewer guidance requires an explanation of observed behavior and coverage gaps. ## Follow-up T3 runtime investigation

The runtime preview at `ef10ff0` published [a clean review](https://github.com/Byntham/crow/pull/12#pullrequestreview-5257644729). It independently passed the ordinary Rust suite, three Python replay tests, and the Chromium fixture, and inspected both fixture screenshots. Its first preparation exceeded the 512 MiB snapshot cap; it recovered by saving dependencies alone and building during the test. Completed-review cleanup removed the prepared snapshots without warnings. Formatting, Clippy and nested Podman were unavailable in that image, while local validation and both architecture CI jobs passed those applicable checks separately.

Further T3 replays exposed a gateway bottleneck. Sixteen completed HTTPS requests could keep their connections open and occupy every tunnel slot. A live isolated reproduction completed each npm metadata GET in about 80–93 ms, retained all sixteen connections, and showed a seventeenth CONNECT blocked until one idle connection closed.

The gateway now keeps at most one accepted connection waiting for a slot. While it is waiting, established tunnels with no traffic in either direction for fifteen seconds release their slots. Ongoing uploads or downloads reset the shared inactivity deadline. Quiet connections without waiting demand retain the existing 120-second whole-connection limit. TLS remains encrypted, so a slow response under pressure can also be interrupted and retried; the private receipt retains that diagnostic.

The same retained-connection probe admitted the next request automatically after the fix. Five new regressions cover demand-driven reclamation, one-way traffic in both directions, clearing demand, byte limits and a closed admission monitor. All seventeen gateway tests passed. The full ordinary Rust suite, formatting, all-target Clippy with warnings denied, three Python replay tests and the managed-container check of twenty-four concurrent downloads also passed.

A standalone pnpm 11.10.0 probe used six exact dependencies from the T3 investigation. The old gateway took 133.6 seconds with recurring 30- and 70-second metadata waits. The fixed gateway completed a run with separate package and metadata caches in 72.4 seconds; two closed-socket retries recovered. These are observed runs, not a controlled speed benchmark: the old run isolated its package store but used the default metadata directory. An earlier 31-second fixed run reused metadata and is excluded from the comparison. Raw probe files remain in ignored worker evidence.

The replays also showed that package-manager `exec` wrappers can verify or reinstall an entire workspace before running a small temporary probe. Offline checks then time out without exercising the application. Reviewer guidance now recommends invoking prepared executables directly for isolated probes when possible, and reserves the package-manager bootstrap runner for invocations of that manager. The user guide now makes the prepared-snapshot cap explicit.


Two targeted T3 continuations completed after the gateway and executable guidance fixes. T3 #12583 ran the actual review-position resolver with the real diff parser and hydrator: ten valid-anchor assertions passed and eight expanded-gap selections returned no anchor. That coverage is head-only because base preparation failed. T3 #12614 ran extracted timeline-row source and generated application Tailwind CSS in Chromium, with synthetic command data. Keyboard focus and collapsed rows also passed, and the reviewer inspected four screenshots. These are component checks, not full T3 application startup.

The failed #12583 base preparation explicitly disabled pnpm retries. A follow-up used the same two dependencies with separate empty package and metadata caches. With retries disabled it failed after 16.3 seconds; with default retries it installed all 55 packages in 33.0 seconds, recovering from four socket errors. This does not establish that the registry itself took fifteen seconds to respond, since reported request duration includes admission waiting. The gateway timeout stays unchanged, and reviewer guidance now preserves normal package-manager retries.

A discovery audit also found that Python projects with both package metadata and requirements.txt installed only the requirements, leaving src-layout packages and their runtime dependencies unavailable. Discovery now groups Python manifests by directory and suggests installing both requirements and an editable package when metadata supports it. Tool-only pyproject files remain requirements-only; ambiguous, malformed or unreadable packaging metadata produces a warning. Regression fixtures cover these cases and unique-project counts beyond the output limit. A real container fixture reproduced the previous missing-package import failure, then passed offline with the editable package, its humanize dependency, pytest, and a separate tool-only project in its own virtual environment.
