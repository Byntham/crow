# Rust migration

Crow is a Linux daemon and CLI, with no browser application or JavaScript plugin API. A native Rust executable replaces the Node runtime, TypeScript build, single-executable injection, and source-versus-binary runtime branching. The existing static website and shell bootstrap remain static assets.

## Decisions

Keep the official external Codex CLI. Replacing it with direct model API calls would change subscription authentication and recovery semantics. The same Crow executable implements the private inspection MCP command.

Use a single Cargo package with modules. Tokio owns asynchronous processes and network tasks; Axum handles inbound HTTP; reqwest with rustls handles HTTPS; rusqlite retains SQLite. A workspace of tiny crates or an ORM would add coordination without an established need.

Preserve configuration version 1, the SQLite records/receipts/events schema, camelCase HTTP payloads, saved job/session files, finding identifiers, and release archive naming. Persisted records and extension-bearing wire envelopes initially use serde_json values with explicit boundary validation. This preserves missing-versus-null distinctions and unknown saved fields without coupling a language port to a schema migration. Internal control flow uses Rust ownership and cancellation handles.

Port behavior before deleting its reference implementation. Existing tests document subtle races, including ownership changes while GitHub calls are pending, durable reports before publication, retrying delivery without rerunning inference, and stale callbacks after supersession. Native tests must exercise these cases, subprocess boundaries, and migration fixtures.

## Required invariants

- A webhook receipt and minimal event commit together before acknowledgment.
- A job has one active lease. Recheck ownership and policy after network waits.
- Preserve incomplete provider sessions. Never silently restart a lost session.
- Save a valid complete report before publishing. Reconcile authenticated bot metadata before retrying publication.
- Repository code is data. Inspect pinned Git objects without checkout, hooks, external diff helpers, or repository commands.
- Enforce provider tools and delegation limits before every new or resumed session.
- Keep author policy, command requester policy, and worker/admin authentication separate.
- Keep initial backlog exclusion, held catch-up batches, and no scheduled PR polling.
- Clean up process groups and join background work before releasing runtime ownership.
- Never claim live subscription/network behavior from synthetic test results.

## Verification and cleanup

Run the original suite to establish a baseline. Build native unit and integration tests using temporary state, loopback GitHub fixtures, and fake Codex executables. Run cargo fmt, cargo clippy, cargo test, release build, and executable/install smoke checks. Replace release automation and documentation. Remove obsolete Node build, SEA, package-manager and source-update code only after the native implementation and relevant tests work.

## Alternatives considered

Embedding or translating JavaScript would retain the Node dependency and its two installation paths. Replacing Codex with direct API requests would change the authentication product. A framework rewrite with a new database schema would introduce a second migration problem. A single native crate keeps the existing process boundaries and lets the runtime and packaging change together.

The port starts at version 0.3.0 so existing 0.2.0 binary installations can recognize it as an update. Static HTML and bootstrap shell remain in their natural formats. The release maintenance command is Rust; the official Wrangler executable is an external website deployment tool.

The original baseline passed 321 tests and skipped five. Native acceptance tests validate the shipped CLI, SQLite service lifecycle, MCP entry point, archived backups, and subsystem behavior. Account-dependent validation remains separate.

## Service execution

The connection service owns a dedicated single-thread Tokio executor. HTTP requests, event processing, publication, catch-up, and control messages run on that executor. Network awaits remain concurrent. Synchronous reads and decisions between awaits cannot interleave on other threads, preserving the original service state machine's atomic transitions. Workers and provider processes use the main Tokio runtime independently. Shutdown cancels and joins the owned service executor and its tasks.

## Compatibility evidence

Differential checks against the original implementation matched 576 configuration validations, 288 repository-setting cases, and 22 complete queue and recovery snapshots. Native fixtures retain the lifecycle checks without requiring Node. The encrypted-backup tests read an archive generated by the legacy implementation.

Two opt-in tests passed against the installed Codex executable with synthetic localhost responses. They checked inspection tool permissions, configured child models, cancellation, saved parent and child identities, and resumed output schemas. These tests did not contact a live model service or alter personal provider state.

## Completed verification

The native default suite passes 169 tests. Two installed-Codex probes also pass in both synthetic subscription and environment-key proxy modes. The proxy probes assert bearer authentication on every parent and child request. Formatting and warnings are checked with Cargo; release smoke checks exercise the extracted executable and its permanent launcher.

The port also repairs interrupted update drains without cancelling active reviews, restores the selected runtime after failed activation, and removes an installer's own launcher if a post-rename durability check fails. Fault-injection tests cover these recovery paths.

The Linux x64 executable is about 11 MiB. Its compressed archive is about 5 MiB including third-party notices. The extracted archive passes checksum, installation, repeat-install, and MCP smoke checks. The optimized executable also passes real service startup, authentication, drain/resume acknowledgment, competing-process exclusion, SQLite integrity, and shutdown tests. Local validation used x64; the ARM64 CI job is configured but was not executed locally. Live GitHub webhooks, advisory publication, corrected-commit review, saved-session recovery, and setup with existing App/proxy/ingress settings passed on testbed PR #5. See [runtime validation](runtime-validation.md). New-account registration and direct live subscription authentication were not exercised.
