# Runtime experiments

Crow's main reviewer can discover project setup, prepare dependencies, run focused commands against pinned base/head commits, and inspect screenshots. The worker's local policy controls availability, images and limits. Repository content and service jobs cannot grant execution authority. Delegated reviewers remain inspection-only. See the [user guide](../user/runtime-experiments.md) for configuration and supported environments, and ADRs [0009](../adr/0009-run-opt-in-isolated-experiments.md) and [0010](../adr/0010-autonomous-runtime-preparation.md) for the decisions.

## Execution and evidence

`runtime.rs` reads manifests from pinned Git objects and suggests setup/test commands. The reviewer checks these against project documentation and CI. Crow builds its embedded managed image, never a repository Dockerfile. Custom immutable local images remain supported.

`execution.rs` owns authorization, budgets, rootless Podman containers and durable receipts. A file lock serializes runtime calls across MCP connections and resumes. Each attempt starts with a receipt and counts against the review limit, including failures. `runtime_diagnostics.rs` records stages and separates command failures from artifact or cleanup warnings. Bounded logs retain both their beginning and end. `runtime_status.rs` derives public progress from receipts; detailed errors stay on the worker.

Preparation runs at one pinned commit and saves a bounded workspace snapshot after success. Identical preparations can be reused only within that review, commit and image. Tests restore the snapshot into a fresh offline container, then restore tracked source from Git to undo setup-hook edits. Helpers run with Python's isolated mode. Crow never extracts repository or prepared archives on the host. Files generated by one experiment do not survive into another; reusable outputs must be part of preparation.

Containers have no credentials, Linux capabilities or privilege escalation. The root filesystem is read-only, resource limits are verified before repository code runs, and time, processes, storage and output are bounded. Tests receive no host mounts or external network. Rootless containers share the host kernel; dedicated VMs remain appropriate for hostile multi-tenant workloads.

Containers remain alive while Crow exports a workspace or requested screenshots, then are removed. Bounded PNG decoding precedes storage and native MCP image delivery through `read_artifact`. Receipt provenance accompanies images. They are not automatically hosted on GitHub. Review instructions require equivalent base/head checks before attributing regressions and visual evidence for visual claims. Model-directed investigation does not guarantee coverage of every changed path.

## Dependency gateway

During preparation only, a read-only private Unix socket mount connects a loopback proxy to `downloads.rs`. The gateway permits selected public package hosts on port 443. It validates the CONNECT host and initial TLS server name, rejects missing SNI and encrypted ClientHello, rejects private/special DNS answers, and connects to a validated address. It forwards no worker credentials. TLS parsing, traffic, connections and deadlines are bounded. Under full capacity, idle tunnels may be reclaimed to admit a waiting download; a silent slow request can therefore need a package-manager retry.

TLS remains end-to-end. The gateway cannot inspect encrypted HTTP hosts, paths or uploads, and an allowed service may support domain fronting to another tenant. This restricts dependency access but does not guarantee tenant identity or prevent all uploads. SELinux socket labeling does not alone establish host-policy compatibility; enforcing configurations remain unvalidated. See the [gateway limits](../user/runtime-experiments.md#what-crow-does).

## Recovery and retention

Cancellation waits for command cleanup; a container deadline also bounds work if Crow exits abruptly. Provider exit independently retries receipt-owned container removal. Interrupted receipts are reconciled before further runtime work, and cleanup failures retain ownership records for retry.

`runtime_cleanup.rs` performs serialized maintenance at startup, hourly and after reviews. Accepted reports and terminal jobs release prepared snapshots; active and paused jobs retain them. Package caches, installed dependencies and build outputs never cross review boundaries. The toolchain image is shared. Maintenance removes only recorded Crow resources and protects configured/current images and images needed by resumable reviews. It never runs a global Podman prune. Logs and screenshots follow ordinary review retention. `crow status` exposes maintenance warnings and `crow cleanup` retries cleanup.

See [runtime validation](../maintainer/runtime-validation.md) for maintained tests and archived model evaluations.
